
5. Provide a Background/Overview of your proposed research area. Conclude with the problem you are trying to solve in this area.
Max 300 words (10% under minimum i.e. 270 words).

In the logistics IT sector there has been a trend to move towards event driven architecture using technologies such as Kafka using a Domain Driven Design approach. These asynchronous communication systems are used to publish events that occur in the business including when a parcel enters a logistic centre (Logistic Center Domain) or when a parcel is delivered (Delivery Tour Domain). Each domain publish its events into a Kafka topic which is seen as a single source of truth for that event and stored in the cloud. All other domains interested in that event would listen to this topic. Using the domain driven design approach the various IT systems responsible for producing these events are decoupled and are only responsible for the data that they produce. This works well when domains want to read one event from a topic at a time. However, what happens if the customer website (Customer Domain) needs to see all events relating to a shipment? An aggregation of events is required and that data needs to be searchable. This can be achieved by aggregating kafka events and creating a graphql api that can then be called by the domains the require data. This api could run in the cloud, for example in a pod on Kubernetes cluster running on Azure Kubernetes Service (aks). However, we now have a mission critical point of failure. If there is an issue with this api then the websites, user phone applications and company branches are suddenly not able to query and data relating to shipments. Therefore, there is a need to provide resilience and redundancy for this cloud service. 

Q: How can an event streaming, cloud based, domain driven architecture provide high availability for the aggregation of events while not drastically increasing complexity or cost?

7. What are your Research Aims & Objectives (Research Question(s))?
Please provide your initial aims/objectives or research question(s) to help us understand your proposed research further.

Aim:
Evaluate high-availability methods for a cloud based event streaming aggregation service used in a domain driven system. Compare the trade-offs of cost, complexity and resilience.
 
Objectives:
1.	Review literature revolving around cloud resilience, Kubernetes availability, event-driven architecture, domain-driven design. 
2.	Design and build a prototype event aggregation set up which then exposes its data via an api and hosted in Kubernetes. 
3.	Deploy and test the prototype using various high availability set ups such as; pods replication, multi node setups, geo redundant cluster deployments, blue/green deployment, or decentralised domain specific deployments.
4.	Measure and collect metrics associated with the various set ups, such as service availability, recovery time, complexity for operations, and operational cost.

9. Detail your approach (steps/procedures) for completing this research. 
Max 200 words. Please - Identifying a question, literature survey plan, qualitative/quantitative analysis and evaluation.

1. Question

How can an event driven infrastructure using event streaming be made more resilient at the data aggregation api level in an domain driven design environment. 







2. Literature Review Plan

Research event streaming, research aggregation of event data for use by consuming domains.
Research Kubernetes and aks setups with high availability.
Investigate common Domain Driven Design patterns for a decoupled architecture while ensuring high availability. 
Investigate load balancing for calls the a graphql running in Kubernetes. 




3. Implementation 
I propose to test out various strategies for providing high availability for the data aggregation api while running in the cloud. I propose to do this with Kubernetes since it is widely adopted for enterprise level container orchestration while being vendor neutral, an important fact when considering sovereignty. I would perform these test on a prototype basis. I propose to use Azure cloud for my implementation, where a free tier for Kubernetes exists that will allow me to test my hypotheses. Azure devops pipeline can also be used for free to deploy the final artefact. 






4. Analysis & Results
With the previously mentioned implementation set up I would then run tests on the various solutions. I would monitor (using Azure monitoring solutions) various metrics such as cost, time, availably and fail over response time. For example, I would manually create an issue with the graphql api (such as killing the pod) and then record the resulting behaviour and its effects such as potential for critical failure, blast radius, recovery time, operational complexity for rollbacks etc. 





10. You are required to create an artefact to answer your research question(s). What artifact will you produce and how can the results of this artifact be measured?
Max 200 words.

I will create a 2 part artefact. 


The first part will be the core artefact which will include event streaming based producers. These could be containerised .NET console apps running in kubernetes that will simulate data and push it to an event streaming setup such as kafka or Azure Events Hub. A consumer will aggregates the events and stores them in a database which is then accessible via a graphql api (the various domains will want custom views.). The graphql will be set up to run as a container in a kubernetes pod while the data store will be in a managed cloud database (eg. Azure PostgreSQL). I will also create a service that reads from the graphql api and displays data in a simple UI frontend website (customer website for updates in shipment). I will set this up locally first on my laptop and then test in Azure.


The second part of the artefact will include various variations of how the aggregation logic and graphql api is hosted in the cloud/Kubernetes. This is the core research area. Metrics will be measured on the availability, recovery time, cost and complexity of the various deployment strategies.
